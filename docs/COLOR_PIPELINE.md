# Owned SDR float color pipeline

Lumen evaluates grades in its own NumPy float32 code (`lumen/color.py`), not an 8-bit FFmpeg grading filter chain. The original SDR input path is explicitly assigned Rec.709, sRGB, or linear Rec.709 RGB; output is encoded Rec.709 RGB, with shape `[..., 3]`. All three assignments require Rec.709/sRGB primaries and D65. Negative values and values greater than one are valid working values. No implicit image clipping or integer conversion occurs in the evaluator. This is an explicit SDR Rec.709 working space, not an OCIO implementation, HDR pipeline, ICC-managed viewer, or ACES workflow.

Schema29 adds a separate, explicit and narrow experimental Apple Log 1 / BT.2020 ingress with an actual tone/gamut rendering step before this creative SDR stack. Its strict profile, float64 normalization precision, fixed shoulder and limits are defined in [APPLE_LOG_INPUT.md](APPLE_LOG_INPUT.md). It is not a relaxation of the default SDR metadata policy below.

## Original SDR input normalization (project version 6)

`Grade.input_encoding` is one of `rec709` (default), `srgb`, or `linear_rec709`. It is stored per clip, participates in undo/redo and render-cache identity, survives splitting/copying, and is independent of the creative grade's enable switch. Old version 1–5 projects without the field retain the original Rec.709 interpretation; source tag fields migrate to `unknown`.

- Rec.709: exact identity, including extended working values.
- sRGB: apply the IEC 61966-2-1 inverse transfer, then the existing BT.709 OETF. The inverse is `E / 12.92` for `E <= 0.04045`; otherwise `((E + 0.055) / 1.055)**2.4`. The forward sRGB helper uses `12.92*L` for `L <= 0.0031308`, otherwise `1.055*L**(1/2.4) - 0.055`. Negative evaluator inputs use an explicitly chosen symmetric extension, not a claim about encoded source-file ranges.
- Linear Rec.709: apply the BT.709 OETF directly.

The [ICC sRGB registry](https://registry.color.org/rgb-registry/srgb) and [sRGB specification](https://registry.color.org/rgb-registry/files/sRGB.pdf) provide the sRGB primaries, D65 white and transfer constants. The matching [BT.709 registry](https://registry.color.org/rgb-registry/bt709) confirms common primaries/D65, so these assignments do not require a gamut conversion matrix. This is transfer-only normalization of relative RGB. It does not perform a scene-to-display appearance transform, chromatic adaptation, BT.1886 display rendering, ICC profile processing, monitor calibration, or camera Log conversion. In particular, it does not promise visual appearance matching across differently calibrated displays.

Normalization runs exactly once before the creative stack below. Before comparison retains input normalization and stabilization, and bypasses spatial restoration plus creative controls/LUTs. Disabling the creative grade alone retains normalization and independently enabled restoration. They do not show raw sRGB/linear code values as Rec.709. Resetting creative controls preserves the input assignment.

### Source metadata and codec boundary

`color_source.py` supplies a shared strict parser used by both media import and the RGB48 render bridge. Media retains transfer, primaries, matrix and range tags for the inspector. `RenderEngine.preview()` and new renders re-read actual files, including on engine preview-cache hits, and include resolved source metadata and explicit assignment in cache identity. Merely switching the UI to an already-built Before/After playback file does not re-probe the source. A known transfer tag must match the selected encoding: `iec61966-2-1` requires sRGB; `linear` requires Linear Rec.709. Conflicts produce an actionable error instead of silently overriding either selection or tag.

On the default SDR path, only BT.709 primaries or explicitly documented missing-primary assumptions are accepted. Tagged BT.2020, P3, PQ, HLG, unsupported Log transfer functions and HDR side metadata are rejected. The only separate exception is the explicitly imported experimental original Apple Log profile linked above; it does not override contradictory SDR/HDR tags or add generic wide-gamut support. Untagged camera Log cannot be identified reliably; choosing one of these three encodings does not make it a supported Log conversion.

YUV matrix/range decoding uses [FFmpeg's zscale/libzimg input controls](https://ffmpeg.org/ffmpeg-filters.html#zscale-1), separately from float transfer normalization. BT.709 matrix and limited/full-range YUV are tested. BT.601 matrix spellings `bt470bg`/`smpte170m` are accepted only when source primaries are explicitly tagged BT.709; this is matrix decoding, not a BT.601-primary gamut transform. Unknown YUV matrix/range is assumed BT.709/limited. Legacy `yuvj` means full range; a contradictory limited tag is rejected. Full-range RGB is decoded directly. Explicitly limited-range RGB is rejected because the tested FFmpeg/zimg RGB path did not expand it reliably. Convert those files to full-range RGB or correctly tagged supported YUV first.

Untagged RGB defaults to full range and missing primaries are assumed Rec.709; the inspector calls these assumptions out. Transfer assignment is always explicit, never automatic color management. The RGB48 decoder is a bounded 16-bit unsigned ingress: negative/super-white source values can be clipped there. Geometry resampling also precedes the float evaluator. Floating-point headroom is preserved inside the evaluator, but this is not an unbounded floating-point codec path or HDR workflow.

Final frame tags explicitly identify the existing normalized Rec.709 output, rather than relying only on encoder flags that may be overridden by unspecified frame metadata. `setparams` labels already-produced pixels; it is not a gamut or transfer conversion. The default compositing/delivery path remains 8-bit YUV 4:2:0 H.264. An explicit ProRes 422 HQ profile now branches directly from RGB16 graded caches through RGB16 geometry, BT.709 limited-range zscale and forced yuv422p10 track composition, to a 10-bit YUV 4:2:2 MOV. Existing basic captions are burned directly into the 10-bit composite with a capability-checked native drawtext path; unsupported FFmpeg builds fail closed rather than reducing the video to 8-bit. Text colors retain the existing RGB style values, interpreted as encoded Rec.709, and blending is in nonlinear code values, not linear light. Verified static PNG stickers use a capability-probed native 10-bit FFmpeg overlay, preserving the high-bit background. The 4:2:2 background is explicitly nearest-expanded to 10-bit 4:4:4, art becomes 10-bit YUVA 4:4:4, and alpha is composed before area-reducing the result to 10-bit 4:2:2 delivery. This avoids pre-subsampling transparent art edges and attenuating chroma twice. The behavioral capability check covers the complete conversion/composition chain. Capability-checked Gaussian blur runs on native gbrp16le after the fitted RGB16 grade cache and before clip transforms, using encoded Rec.709 code values rather than linear light. Runtime precision/behavior probes and the high-bit render forbid automatic conversion filters. Animated JSON frame packs, active vignette and unverified clip effects still fail closed rather than entering an unverified low-bit branch. See [bounded high-bit effects](HIGH_BIT_EFFECTS.zh-CN.md). See [high-bit caption boundaries](HIGH_BIT_CAPTIONS.zh-CN.md). Disabled/zero-amount effects and disabled stickers remain exact bypasses. Both paths share the same bounded RGB16 source/grade cache; the high-bit profile never reuses a final 8-bit preview cache. See [delivery foundation](COLOR_FOUNDATION.zh-CN.md). Sticker artwork is still rasterized by Qt into an 8-bit RGBA asset-only layer. This retains legacy gamma-coded SDR numeric appearance and encoded Rec.709 interpretation; it does not apply sRGB-to-Rec.709 transfer normalization, linear-light blending, ICC or HDR color management. Keeping the background video high-bit does not add precision to the asset layer. See [static PNG composition boundaries](HIGH_BIT_STICKERS.zh-CN.md). Full color-managed composition/monitoring remains future work.

## Fixed evaluation order

1. Decode Rec.709 with the inverse OETF. Apply optional neutral-reference white-balance gains in linear RGB, then `linear_exposure` as multiplication by `2**stops` in linear light. See [the bounded reference contract](WHITE_BALANCE.md).
2. Apply per-channel lift/gamma/gain: `v = (linear + lift) * gain`, then `sign(v) * abs(v)**(1/gamma)`. This defined RGB arithmetic is not a claim of matching another product's color wheels. Neutral lift/gamma/gain are 0/1/1.
3. Encode with the Rec.709 OETF. Steps 1–3 are skipped when all linear operations are neutral, preserving bit-exact identity.
4. Legacy `exposure` multiplies encoded RGB by `2**exposure`. This retains old projects' code-value gain semantics; use Linear exposure for physical light ratios.
5. Contrast scales encoded RGB about `contrast_pivot` (default 0.5): `(rgb - pivot)*contrast + pivot`.
6. Saturation mixes around encoded luma `Y = .2126 R + .7152 G + .0722 B`: `Y + saturation*(rgb-Y)`.
7. Temperature/tint add RGB offsets `[t + q/2, -q, -t + q/2]` where `t=.25*temperature`, `q=.25*tint`. These are creative controls, not a chromatic-adaptation or Kelvin white-balance model.
8. Shadows/highlights add equal RGB offsets `.5*(shadows*(1-Y)**2 + highlights*Y**2)`, using the current encoded luma clamped to [0,1] for mask weights only. Image values themselves are not clamped.
9. Master curve, then separate R/G/B curves. Curves use piecewise-linear interpolation and terminal-segment linear extrapolation. X positions strictly increase. Project curves have 2–32 points, X endpoints 0 and 1, Y in [-1,2]. Non-monotonic Y is permitted for creative inversions. Identity curves return exact copies.
10. Optional circular Hue-vs-Hue and Hue-vs-Sat curves sample the original post-RGB-curve hue. Their defaults are exact arithmetic bypasses. Hue offset uses generalized HSV reconstruction; saturation scales around the rotated encoded Rec.709 luma. Both endpoints of each piecewise-linear curve are linked for periodic continuity. Achromatic pixels are unchanged and working RGB is not clipped. See [the precise selective-color contract](SELECTIVE_COLOR.md).
11. Optional 3D `.cube` LUT uses float32 trilinear interpolation, with red changing fastest in file row order. LUT input coordinates are explicitly clamped to the declared domain, default [0,1]. This is the only RGB sampling operation that bounds LUT coordinates; LUT output values can remain negative or greater than one. Use no LUT or zero strength if unbounded working headroom is required. Strength 0..1 blends the pre-LUT and LUT-result encoded Rec.709 RGB at this stage; zero bypasses file loading, one preserves full-strength legacy behavior. The blend adds no output clipping.

Bypass or a disabled grade returns an independent float32 copy of normalized input; with the default Rec.709 assignment this is bit-exact to the original input. All stages share the same evaluator for preview/export integration. Non-finite input and output are errors. The evaluator requires float32 input, does not mutate it, and introduces no 8-bit intermediates.

## Transfer definitions and limitations

The OETF uses the published rounded BT.709 constants: `4.5*L` below 0.018; `1.099*L**0.45 - .099` otherwise. The inverse uses encoded threshold 0.081. Negative values use the symmetric extension; above-one values continue the same power law. References: [ITU-R BT.709](https://www.itu.int/rec/R-REC-BT.709) and the symmetric extension in [ITU-R BT.2380-1](https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2380-1-2017-PDF-E.pdf).

The rounded published coefficients have a small discontinuity at the toe. Consequently round-trips in the tiny encoded interval around 0.081 are not strictly invertible. Neutral operations avoid this round-trip entirely. This is the inverse camera OETF, not a BT.1886 reference-display EOTF. It does not recover unknown original scene radiance or calibrate a display. The signed extension is an explicit application choice.

The new creative display controls have explicitly defined float arithmetic and are not pixel-identical replacements for FFmpeg's old quantized eq/hue/colorbalance implementation. The legacy exposure semantics are retained; previous grades using other controls may need adjustment.

3D LUT parsing supports TITLE, LUT_3D_SIZE (2–65), DOMAIN_MIN and DOMAIN_MAX. It rejects duplicate/late headers, unsupported 1D/combined LUTs, malformed/non-finite samples, invalid domains and wrong sample counts. A 64 MiB file limit bounds parsing. Parsed LUTs are cached by their complete file bytes, while active render fingerprints include the SHA-256 content digest; same-size edits with preserved timestamps still invalidate the look. It does not infer the LUT's expected color space; users must supply an SDR encoded Rec.709 LUT.

## Final output boundary

The media bridge clips encoded RGB to [0,1] and quantizes it to RGB16 immediately after the entire owned grade/restoration stack. Final delivery additionally quantizes to its explicit 8-bit or 10-bit YUV format. This is not a float-through-composition master. The float evaluator intentionally does not do so. A true linear exposure recovery or opposing float operation therefore retains recoverable over-range data until this boundary, except when an explicitly bounded LUT has already sampled it.

Tests cover transfer references, signed ranges, neutral/bypass exactness, true linear ratios, legacy code gain, LGG, curve order/extrapolation, LUT axis/domain behavior, invalid LUTs, numerical display controls and an 8192-step neutral ramp without 8-bit quantization.

Input-foundation tests additionally cover sRGB reference values and signed round trips; normalization order, bypass and prevention of double conversion; version 1–5 migration, persistence, undo and invalid-transaction rollback; malformed metadata, known assignment conflicts and unsupported HDR/gamut rejection; actual tagged RGB16/sRGB and linear media; independent 10-bit YUV BT.709/BT.601 matrix and full/limited range references; limited-RGB rejection; source-metadata cache invalidation; and decoded preview/export consistency. Fixture creation assigns rawvideo source tags before FFmpeg's `-i` as well as output tags and verifies resulting metadata, preventing accidental conversion of the test data itself.

## Optional spatial restoration stage

With schema 9, enabled nonzero restoration runs after source normalization and before the creative stack, in normalized Rec.709-encoded float32 RGB. It processes only the active-picture rectangle, never synthetic letterbox padding. Existing stabilization is applied in source-encoded RGB before normalization. This is not linear-light or HDR restoration. Disabled/all-zero restoration preserves the previous decode/grading path. See [restoration scope and tests](RESTORATION_MILESTONE.md).


## Preview scopes and creative-grade transfer

`color_scopes.py` adds separately measured R′G′B′ parade and a BT.709 Cb/Cr vectorscope, retaining histogram/luma modes. These analyze bounded point samples of Qt-decoded 8-bit preview RGB, not the high-bit master. No second limited-range expansion or linearization is applied. Scope identity is tied to the active preview revision/mode; stale data is labeled and source changes clear it. Reference targets explicitly mean 75%/100% encoded RGB amplitude, not saturation percentages. Independent math/count/padded-row/geometry/UI tests define the contract.

`grade_transfer.py` copies all creative Grade fields except `input_encoding`. Paste prepares and validates an independent candidate before one editor transaction, preserving the target source assignment and every non-grade field. The per-window in-memory copy never touches the system clipboard. Assigned LUTs, including bypassed ones, must remain the same readable, parsed local file by resolved path and SHA-256. Missing/changed/invalid files fail atomically. No-op paste does not create undo history or mark the project changed.
